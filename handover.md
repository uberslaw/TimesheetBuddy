# Handover — Timesheet Buddy 3.0

## Purpose

Desktop timesheet helper for logging time against job codes through the day. Compact always-on-top window with an active timer, favorites, settings, a “still working?” recheck prompt, and a catch-up check. Every catch-up interval, if some of the last N minutes are not already logged (including a running timer), it asks you to assign tasks to those unaccounted minutes. If a timer already covers the interval, it asks whether you are still on that task instead.

## Data

| File | Contents |
|------|----------|
| `<data folder>\settings.json` | Job codes, favorites, categories, prompt prefs, window position, timer widget toggles (`showTimerWidget`, `showTimerWidgetWhenCovered`, `showTimerWidgetOnOtherMonitor`) + position, job-code view order (`jobCodeViewIds`), all time entries, active session, running No Task Selected start (`noTaskStartedUtc`) and pending unassigned spans (`unassignedSegments`) |
| `<data folder>\day-notes-yyyyMMdd.txt` | Per-day free-text notes from the day log |
| `<data folder>\app-usage-yyyy-MM-dd.json` | App Track: `{ "date", "apps": [ { "exe", "name", "seconds" } ] }` per local day; exe file name (no folder) + friendly name only. Not read by any timesheet total or export |
| `<data folder>\settings.json.bak-yyyyMMddHHmmss` (and `day-notes-….txt.bak-…`, `app-usage-….json.bak-…`) | Left by Settings → Data → Replace / Merge (the target folder's own file before it was changed), by Import data… (settings.json before the import), and by the first load of an older release's file (the original, untouched) |
| `<data folder>\backups\settings-yyyyMMdd.json` | Daily snapshot: settings.json as it was before the first save of each day; the last 7 are kept. Listed in Import data… |
| `<data folder>\journal\<machine>-<clientid>.jsonl` | Change log, one file per install (only that install writes it, so OneDrive never has to merge it). One JSON object per line: `t` (UTC), `client`, `machine`, `action`, `entry` (entry id, optional), `summary`. Own lines older than 90 days are pruned at start-up; files of installs untouched for 90 days are deleted |
| `<data folder>\sessions\<clientid>.json` | Two PCs open: written every 20 s while the app runs, deleted on exit. `clientId`, `machine`, `processStartUtc`, `lastHeartbeatUtc`, `confirmedActiveAtUtc`, `closeRequest { targetClientId, targetProcessStartUtc, requestedAtUtc, byClientId, byMachine }`, `todayDate`, `todayEntries`, `running` (the unsaved running timer). Never copied or moved with the data |
| `%LocalAppData%\TimesheetBuddy\client.json` | This install's id, `{ "clientId", "machine" }`. Always in the local default folder (never in a shared one); a new id is made if the machine name changes, so a copied profile is not mistaken for this PC |
| `<data folder>\app-usage-….json.unreadable-yyyyMMddHHmmss` | An app-usage file that would not parse, set aside so the next save does not overwrite it. Not copied when the folder changes |
| `%LocalAppData%\TimesheetBuddy\datafolder.json` | Pointer to a custom data folder, `{ "dataFolder": "D:\\…" }`. Always in the default folder; absent or blank = default |
| `%LocalAppData%\TimesheetBuddy\crash.log` | Unhandled exceptions. Always in the default folder, even with a custom data folder. Startup failures also show a dialog with this path |

The data folder is `%LocalAppData%\TimesheetBuddy\` unless `datafolder.json` names another one. `App.OnStartup` calls `DataFolder.Resolve`: if the named folder is missing or not writable (e.g. an unplugged USB or network drive) the session uses the default folder, nothing is created in the missing one, the pointer is left as is (so the next start uses it again once it is back), and one warning names the missing folder after the window shows.

**Changing the data folder (Settings → Data).** Happens when the user confirms, not on Save (Cancel does not undo it; the tab says so). Browse… opens `OpenFolderDialog` ("Choose a folder for Timesheet Buddy data", starting in the current folder); Use default targets `%LocalAppData%\TimesheetBuddy`; Open folder runs `explorer.exe` on it. `DataFolder.Plan` decides: same folder → nothing (except, after a fallback, picking the folder in use clears the stale pointer); missing or not writable (temp file create/delete fails) → error, nothing changes; otherwise `DataFolderChoiceWindow` opens. For a folder without `settings.json` it asks OK / Cancel; for one with data it offers **Use existing**, **Merge** and **Replace**. Both show **Move my data: delete it from the old folder once the copy is checked**, ticked by default for an empty folder and unticked when the folder already has data (`DataFolder.DefaultMove`). **OK / Replace** (`CopyAndSwitch` → `DataFolder.Transfer`): save in-memory state to the old folder, flush App Track, copy `settings.json`, `day-notes-*.txt`, `app-usage-*.json`, the `backups\` snapshots and `journal\*.jsonl` the target lacks (a target file that would be overwritten is renamed `….bak-yyyyMMddHHmmss` first), compare every copy with its original by SHA-256, then switch the store, save to the new folder and write the pointer; if any of that fails the copies are deleted, renamed files are put back and the old folder stays in use. Only after that, with Move ticked, each original that is still byte-for-byte what was copied is deleted (a file that can't be deleted is listed and left). `client.json`, `crash.log`, `datafolder.json`, `sessions\` and `.tmp`/`.bak`/`.unreadable` leftovers never move. **Merge** (`MergeAndSwitch` → `DataImport.MergeFolder`): the target's `settings.json` is backed up, the current entries, job codes, categories, favourites and No Task Selected spans are added to it (same id: the current copy wins; tombstones respected), day notes are appended under a separator and App Track days merged per program, the result is read back and must hold everything, then the store switches and saves (which pulls the folder's entries into the open window; a running timer keeps running), and with Move ticked the old data files are deleted. **Use existing** stops a running timer and saves everything to the old folder (the dialog warns about the timer), writes the pointer, says it will restart, starts a new copy of the exe and shuts down. Every change is journalled (`folder change`), the old folder's session file is deleted and the presence heartbeat runs at once in the new folder. Check: `dotnet run --project tests/DataFolderCheck`.

**Saving (OneDrive-safe).** `SettingsStore.Save` writes `settings.json.tmp` and moves it over `settings.json` (`IoRetry.WriteAllTextAtomic`), retrying sharing violations for about 3 s (50 ms doubling to 1.6 s), so a OneDrive or antivirus lock never leaves a half-written file. Before writing it compares the file with the copy it last read or wrote: if another PC changed it, the two are merged three ways against that baseline (`SettingsMerge.Concurrent`: union by entry id, an entry edited on one side only takes that edit, edited on both takes the later `modifiedAtUtc`, list items likewise). Entries deleted for good are remembered as tombstones (`removedEntries`, kept 400 days) so a merge never brings them back. Every save sets `formatVersion` (2) and stamps changed entries with `createdByClientId/Machine`, `modifiedByClientId/Machine` and `modifiedAtUtc` (omitted when empty; older files load without them). Every 20 s `SettingsStore.Pull` merges another PC's saved changes into memory without writing, so two open PCs never answer each other's saves. A running timer is never merged across PCs: open entries are skipped and an `activeSession` stamped with another client id is dropped on load. The first save each day copies the previous file to `backups\settings-yyyyMMdd.json` (7 kept). Check: `dotnet run --project tests/SyncCheck`.

**Data from older releases.** Every load and Import data… read through `SettingsStore.ParseWithUpgrades` → `LegacyData`, a list of `ILegacyReader`s (text, JSON and model passes; add one to `LegacyData.Readers` for a new shape). Shapes found in the git history, all of the 3.0 line: the first release ("Import Timesheet Buddy 3.0") stored `windowLeft`/`windowTop` as non-nullable doubles defaulting to NaN (`"NaN"` or bare `NaN`, which strict JSON rejects) → cleared so the window is placed fresh; entries' `jobCodeText` held the full `"CODE — Description"` label → shortened to the current label when the code id is known; a running timer was saved open (active session + entry without an end) and resumed → manual entries without an end are closed after their minutes, a session without its entry is restored as an entry, and the open timer is then finished as usual; fields added later (ticket, soft delete, window height, job-code view, widget, No Task Selected, App Track, tombstones, stamps) read as defaults. The file name, `%LocalAppData%\TimesheetBuddy` and `day-notes-yyyyMMdd.txt` never changed, and nothing was ever renamed. A file without `formatVersion` is recognised as an older release (`LegacyData.Release`: "3.0", "3.0 with early updates" or "3.x (Nov 2026 updates)"); on its first load the original is copied to `settings.json.bak-yyyyMMddHHmmss` before anything is written. No file format from before 3.0 exists in this repository, so pre-3.0 files are not specifically handled (they are read leniently: unknown properties ignored, unreadable items skipped). Check: `dotnet run --project tests/LegacyDataCheck`.

**Change log.** `ClientIdentity` gives each install a GUID (`client.json`, local only) and the machine name. `ChangeJournal` appends one line per action to `journal\<machine>-<clientid>.jsonl` in the data folder: start, stop, add, modify (renames coalesced after a 5 s pause), move, delete, restore, import, folder change and overlap (also open, Yes / Not now, kept / discarded, closed on request). Appending never throws. Menu → Change log… merges every PC's file, newest first, with the machine on each line; range Today / 7 / 30 / 90 days, This PC only, Refresh and Open folder.

**Two PCs open on one data folder (OneDrive).** Each running app writes `sessions\<clientid>.json` at start and every `PresenceTiming.Heartbeat` (20 s), and reads the other session files then (also once at start and right after an unlock). Another session is live when its heartbeat is under `PresenceTiming.LiveWindow` (90 s) old and its client id differs; another install on the same machine name is ignored. The constants are in `Services/Presence.cs`. Activity is not inferred from input (no `GetLastInputInfo`). With a live session on another PC, `OverlapRules.Decide` shows a non-modal, non-activating popup, bottom-right: "Timesheet Buddy is also open on <PC>. Are you active on this one?" with Yes / Not now (✕ = Not now). Both PCs show it independently. While Windows is locked (`ScreenLockWatcher.IsLocked`, probed at start with `OpenInputDesktop`/`SwitchDesktop`) the popup is held back and shows after unlock; being locked never counts as Yes or No. Not now leaves both running and is not asked again for that session until the other app restarts. **Yes** writes `confirmedActiveAtUtc` plus a `closeRequest` aimed at the other session's client id and process start, then opens Keep / Discard: "Timesheet Buddy is open on <PC>. These are today's entries: … and this one is active: <task, elapsed>. Would you like to keep any of this data or discard?", listing the other PC's today entries from its session file (so its unsaved running timer is included, as a finished entry ending now, or at its last heartbeat if it has stopped), with checkboxes; entries already here (same id) are shown greyed out and can't be ticked, entries deleted here are not offered. Keep selected adds the ticked ones and saves; Discard all keeps nothing; both are journalled. **The other PC**, on its next heartbeat, finds the request and closes at once without saving (`App.CloseWithoutSaving`): `ClosingWithoutSave` is set, the store is suspended (no on-exit timer save, no settings.json or day-notes write, no App Track flush), it journals, deletes its session file, dismisses its popups and calls `Application.Shutdown`, whatever its popup state and even while locked; a background thread ends the process after 3 s if anything blocks. **Both said Yes:** the earlier `confirmedActiveAtUtc` wins (tie: the smaller client id); the later one shows "Already confirmed on <PC>." for 4 s and closes the same way. **Neither:** both keep running; each save merges the other's changes and the 20 s pull shows them. A request only matches the exact process start, and the Yes and request are cleared once the other session is gone, so a stale file can never close a later launch. Sequential use (close at home, open at work) needs nothing: a session file older than 90 s is ignored and the load merges the latest file. Timings: detection needs the other PC's session file to sync (OneDrive, usually seconds to a minute) plus up to 20 s for the next heartbeat; the close happens within the same delay after Yes. Entries made on the closing PC in that window (after its last heartbeat reached this PC) are lost by design. Check: `dotnet run --project tests/PresenceCheck`.

Defaults seed a few job codes (`ADMIN`, `DEV`, `MTG`, `SUP`) and sample favorites on first launch.

Closing the app while a timer is running saves that task onto the current day's list as a finished entry (end time set). It does not resume after restart. The one exception is a close requested by another PC (see Two PCs open), which saves nothing.

**No Task Selected.** Any user stop (main Stop, job-code view Stop, widget Stop, the still-working dialog's Stop, deleting the running task, loading an older day) starts a "No Task Selected" timer from the same instant; `AppState.StartOrSwitch` from anywhere ends it. Closing the app (`AppState.StopAllForShutdown`) finishes the running task without starting idle time and closes any running idle run into pending; nothing is started on launch, and a running start left in settings.json by a crash is dropped on load (its end is unknown). A run under 1 minute is discarded; 1 minute or more becomes pending. Storage is separate from time entries: `noTaskStartedUtc` (running start, nullable) and `unassignedSegments` (`startUtc` / `endUtc` pairs) in settings.json. Because every total reads `Entries`, unassigned time is never in the band Total, Time Remaining, job-code rows, the job-code view, Today by task, Weeks & export, PDF or Excel. The main window shows it as a muted italic "No Task Selected" row in the band (today's pending plus the running run; not added to Total), and while it runs the big counter shows the idle elapsed time and the status line reads "No Task Selected". Open time is pending plus the running run once it reaches a minute, minus anything an entry already covers (e.g. Add time over that span). On each catch-up interval (same `FifteenMinuteIntervalMinutes` cadence), if open time is at least 1 whole minute, `NoTaskAssignWindow` opens instead of any other catch-up dialog: "{n} minutes were logged as No Task Selected. Where should they go?", with the same rows as the old catch-up grid (task, category, common task/favorite, comment, job code, minutes), Add row, All to Break (`Break` / `Break`, no job code), Not now (stays pending, asked again next interval) and Assign. Minutes must be positive and at most n (whole minutes, rounded down). Assigned entries (`source: "no-task"`) are placed inside the open spans latest first, so they never overlap each other or logged time; the rest stays pending (a leftover under 1 minute is dropped). If idle is running and has reached a minute when you assign, it is closed at now for the assignment and restarts from now. The unaccounted-minutes check treats pending and running idle spans as covered, so the same minutes are never asked about twice, and one tick shows at most one dialog. The screen-lock prompt still only follows a running task. If the catch-up prompt is turned off in Settings, pending time just stays pending and visible. Check: `dotnet run --project tests/NoTaskTimeCheck`.

**When the widget shows.** The rule is "the user can't see the main window on the primary monitor". `MainWindow.UpdateTimerWidget` gathers a `MainWindowSnapshot` and `WidgetVisibilityRules.Decide` returns, in order: hide while closing, while the master is Disable, or while a modal dialog (any prompt, Settings, Day log…) is open (`ComponentDispatcher.IsThreadModal`); show if minimized; show if hidden (`Visibility != Visible` or `!IsVisible`; always counts with the master on); show if the "another monitor" option is on and the main window's centre (`GetWindowRect`) is outside the primary monitor's bounds (`MonitorFromPoint(0,0, MONITOR_DEFAULTTOPRIMARY)` + `GetMonitorInfo`; both in the thread's DPI coordinate space, a failed probe counts as on the primary); show if the "covered" option is on, the main window is not pinned (`Topmost`) and at least `CoveredThreshold` (50%) of it is covered; otherwise hide. Pinned on the primary and not minimized therefore always hides. Coverage (`WindowVisibility.CoveredFraction`) walks windows above the main HWND with `GetWindow(GW_HWNDPREV)` (at most 1024) and counts a window only if it is visible, not minimized, not DWM-cloaked (suspended UWP apps, other virtual desktops), not owned by this process (the widget, dialogs, the job-code view), not `WS_EX_TOOLWINDOW`, not a click-through (`WS_EX_LAYERED | WS_EX_TRANSPARENT`) or alpha-0 layered overlay, not a shell window (`Progman`, `WorkerW`, `Shell_TrayWnd`, `Shell_SecondaryTrayWnd`), and has a non-empty rect (`DWMWA_EXTENDED_FRAME_BOUNDS`, falling back to `GetWindowRect`). `CoverageAccumulator` keeps the uncovered part as disjoint rectangles and cuts each cover out, so overlaps are not double counted; the walk stops as soon as 50% is reached. It runs on StateChanged, Activated, Deactivated, LocationChanged, SizeChanged, IsVisibleChanged, pin toggle and settings changes, and on the existing one-second `_uiTimer` tick (other apps moving in front raise no event here). `WidgetVisibilityGate` adds hysteresis: minimized/hidden show at once and "nothing to show" hides at once (so clicking the main window hides it immediately), while covered / other monitor must hold on 2 consecutive ticks (`StablePollsToShow`) before the widget appears; events never advance that count. Clicking the widget and prompts (`EnsureVisibleForPrompt`) reset the gate, so with the main window on another monitor the widget comes back about 2 s after it is restored. Showing never activates the widget (`ShowActivated=False`, `Show()` only when not already visible, so a drag in progress is never repositioned) and never touches the main window's z-order.

**App Track.** An optional add-on that logs how long each program is in the foreground, separate from the timesheet. Menu → App Track is the first Menu item, a check item (✓ when on); clicking it saves `appTrackEnabled` in settings.json and starts or stops tracking at once. It is off by default (a settings.json without the key reads as off). Settings → Prompts & pin has the same switch as a checkbox, applied on Save. **Privacy:** only the exe file name (no folder, so no user name from the path) and a friendly name are read or stored; window titles, URLs, document and email text are never read (no `GetWindowText`, no UI Automation). Each second (`DispatcherTimer`, Background priority, UI thread) `ForegroundApp.Current` calls `GetForegroundWindow` → `GetWindowThreadProcessId` → `OpenProcess(PROCESS_QUERY_LIMITED_INFORMATION)` → `QueryFullProcessImageNameW`. The friendly name (`AppNames.Friendly`) is `FileVersionInfo.FileDescription`, else `ProductName`, else the exe name without its extension, cached per exe path (`AppNameCache`); Explorer and the desktop show as "Windows Explorer". If the process can't be opened (an elevated app) the process name is used (`Taskmgr` / `Taskmgr.exe`), else "Unknown app". Timesheet Buddy's own windows (the main window, widget, dialogs) **count** as "Timesheet Buddy" (`TimesheetBuddy.exe`) rather than being skipped, since time spent filling in the timesheet is real time. No foreground window credits nothing. Totals are keyed by the exe file name, case-insensitive, so an update that moves the exe (versioned folders) keeps one row; the newest friendly name wins. `AppUsageAccumulator` credits the interval since the previous sample to the current app; a gap over 15 s (sleep, a stalled thread) is not credited. **Idle:** `GetLastInputInfo` gives the time since the last input; time after the last input stays pending (it shows live in App usage but is not saved) and is committed when input arrives. Once idle exceeds `AppUsageAccumulator.DefaultIdleThreshold` (5 minutes, a constant) the pending part after the last input is dropped, so an idle stretch counts nothing, not even its first 5 minutes; accrual restarts on the next input. **Lock:** `ScreenLockWatcher.LockChanged` → `AppTracker.SetLocked`; while locked nothing accrues and pending time after the last input is dropped (an auto-lock after a short idle does not count the idle minutes). **Midnight:** spans are split at local midnight, so the same app gets time on both days. Saved every minute, when App Track is switched off, before a data-folder copy, on window close and on `App.OnExit`, as `app-usage-yyyy-MM-dd.json` in the current data folder (`App.Store.Folder`), written to a `.tmp` and moved into place. A file that won't parse is renamed `….unreadable-yyyyMMddHHmmss` instead of being overwritten. Switching off (or exit) keeps pending time unless idle is already past the threshold. Nothing here touches `Entries`, so App Track never appears in the band, Total, Today by task, the job-code view, Weeks & export, PDF or Excel. **App usage…** (Menu, under App Track) lists the day's programs, longest first: friendly name (exe file name as tooltip), compact time (`DayTotals.FormatCompact`) and whole-percent share of the day's tracked time (`PercentBreakdown.Shares`, sums to 100), with Total tracked at the bottom, ◀ / Today / ▶ (no future days), a live one-second refresh, "Nothing tracked on this day." when empty, and an orange hint while App Track is off. Win32 parts can only be exercised on Windows. Check: `dotnet run --project tests/AppTrackCheck`.

**Screen lock.** If Windows locks the session while a timer is running, unlock (after at least 30 seconds) asks how to assign that time: Assign on the last-active row (job code, category, task name) keeps it there; Assign beside a job-code selector moves the lock interval onto that code. Moving the interval leaves the time before the lock on the original code and continues that code from the unlock moment, so the locked minutes are not counted twice. A lock under 30 seconds, or a lock while the timer is idle, does not prompt.

## Architecture notes

- **No MVVM framework** — code-behind + `AppState` (`INotifyPropertyChanged`) for simplicity.
- **Singletons on `App`**: `App.State`, `App.Scheduler`, `App.Store`, `App.AppTracker`, `App.Client`, `App.Journal`, `App.Presence`.
- **Test projects** under `tests/` are console apps that link the service files they test; `tests/DataLayer.props` holds the shared data-layer files (store, merge, legacy readers, journal, client id) so adding a dependency there fixes every check at once.
- **PromptScheduler** ticks every second; only one modal prompt at a time (`RecheckOpen` / `FifteenOpen`).
- Catch-up measures the last N minutes (`FifteenMinuteIntervalMinutes`, same value the scheduler waits). Accounted time is the union of logged entries plus the running timer's elapsed overlap. A gap under 30 seconds counts as zero. If at least one minute is unaccounted, the assign-tasks dialog opens and the still-working dialog does not. If nothing is unaccounted and a timer is running, the existing still-working window opens instead. If nothing is unaccounted and no timer is running, no popup appears.
- The still-working window stays until the user chooses. Catch-up asks how to assign the whole unaccounted block: last active task, another task logged today, or a newly entered task. Not now dismisses without creating entries.
- Selecting a job code in the main window only fills the selector; **Add** starts the timer. Clicking a Today-by-task row still continues that task at once.

## Contact / ownership

Built as a greenfield Cursor cloud agent project. No external services, auth, or cloud sync of its own — all data is local: the Windows user profile by default, or the folder chosen in Settings → Data. If that folder is synced (OneDrive), the app merges changes from other PCs on save and coordinates two open PCs through `sessions\` (see Data).
